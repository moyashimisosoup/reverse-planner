## 1. 目標と基本ルール

SOFT PIXELは、レトロゲーム風の「押した／収まった／できた」という触感を、短い動きで伝える。常時動き続ける装飾は置かない。

- **即応性**：押した瞬間に反応し、結果を長い演出で隠さない。
- **意味のある動き**：追加は現れる、並べ替えは移動する、完了は状態が確定する。
- **一度だけ**：入口/計画表示/完了の演出を無限ループしない。
- **可読性**：タイマー・数値・入力中の文字をアニメーションで読みにくくしない。
- **公平性**：Reduced Motionやキーボードでも、機能と情報は変化しない。
- **軽量**：CSS transform・opacity中心。レイアウト変更の連続アニメーションは極力避ける。

参考：[モーションリファレンス（TakayuStudio）](https://motion-reference.takayustudio.jp/)。「プレスフィードバック」「スナップイン」「ルートスライド」「リスト順次表示」「ポップスケール」「FLIP並べ替え」「グリッドウェーブ」「アコーディオン展開」「ピクセルディゾルブ」「進捗バー」等を参考に選定。以下のmsと数値は **Reverse Planner向けに調整した設計案** であり、参考サイトのデモ設定をそのまま引用したものではない。

## 4. 詳細ステートと実装ルール

### MO-01: 押すとへこむ立体ボタン

| 状態 | transform | 影 | 補足 |
| --- | --- | --- | --- |
| default | translateY(0) | 0 4px 0 濃い底面色 | 立体感 |
| hover（マウス） | translateY(-1px) | 0 5px 0 | 過度に浮かせない |
| pressed（pointerdown / :active） | translateY(3px) | 0 1px 0 | 75ms程度 |
| released | translateY(0) | 0 4px 0 | 130ms程度 |
| disabled | translateY(0) | 平坦な影・低コントラスト | クリック不可、理由が必要なら説明 |
| keyboard focus | 押下しなくても分かる輪郭 | 影は通常のまま | :focus-visibleで3px程度のリング |

実装上の約束：
- CSSのtransformで「見た目だけ」動かし、レイアウトを動かさない。
- iPhoneでは :active だけに頼らず、適切なpointer処理とhover条件を検証する。JSで持続的pressedを残さない。
- キーボードEnter/Spaceによるアクションにも実行結果が分かる反応を設ける。
- disabledを押したときの反発・シェイクは避ける。

概念例：

~~~css
.pixel-button {
  transform: translateY(0);
  box-shadow: 0 4px 0 var(--button-shadow);
  transition: transform 75ms var(--ease-press), box-shadow 75ms var(--ease-press);
}
.pixel-button:active {
  transform: translateY(3px);
  box-shadow: 0 1px 0 var(--button-shadow);
}
.pixel-button:focus-visible {
  outline: 3px solid var(--focus);
  outline-offset: 3px;
}
~~~

※上記は仕様説明用の断片。最終実装でアクセシビリティ・スマホ動作を確認する。

### MO-02: 画面ルートスライド

- HOME→SETUP、SETUP→PLAN、PLAN→RUNで**進む場合は新画面を右から16～24px**入れ、旧画面を短く薄くする。
- 戻る場合は**逆方向**。「進む／戻る」の関係が分かることを最優先する。
- 基本時間250ms、標準イージング。ページ全体を水平に大移動しない。
- クリック連打で重複遷移が発生しない。ブラウザ履歴/画面状態を先に更新し、描画はその結果へ追従する。
- 画面切替後は見出しへ適切にフォーカスを移し、スクリーンリーダーが新画面を理解できること。

### MO-03: タスクのスナップイン

- 追加ボタン押下後、タスク行はすでに保存・描画済みの状態で、X=16px→0・opacity=.75→1。
- 160～220ms程度。入力欄から追加されたカードへ注意を移し、可能なら新しいカードの編集フィールドへフォーカス。
- 同じリストの全行を毎回再入場させない。編集時は値だけを変える。
- 削除は確認が必要なら確認後に行い、退場アニメは長くても150ms程度。

### MO-04: 完了ポップ

- 完了操作でチェックが 1→1.10→1（拡縮）に戻る。周囲の文字・レイアウトは揺らさない。
- カード背景をミントから淡いピーチへ変更し、完了表示と次の作業への導線を出す。
- 「できた！」の文字は演出に依存せず即時に表示。状態と保存が確定してから次のカードを前面に。
- 成績評価やスコア化、音の自動再生は行わない。

### MO-05: 時系列のリスト順次表示

- PLAN初回表示でカードを**上から下へ**一定の遅延で入れる。
- 初段0ms、その後各カード40～55ms差。各カード180～220msで着地。全体は最大350～450msを上限とする。
- 最初から視認・タップ可能なDOMにしておき、演出の完了を待って計画が操作できる設計にしない。
- 再計算時に全行アニメーションを再起動しない。追加・削除されたカードだけ動かす。

### MO-06: FLIP並べ替え

- First・Lastの位置差を計算して、新しいDOM順は確定したままtransformで視覚的に補間する。
- 180～240msを目安。テキストを斜めに回転させない。
- キーボード操作は↑↓ボタンで可能にし、スクリーンリーダーには「上に移動しました」等の短い通知。
- ドラッグ導入は操作しやすさを確認してから。ドラッグを実装しても上下ボタンは残す。

### MO-07: 右列からのグリッドウェーブ

意図：以前の構想「右から一列ずつ、列の中の正方形カードは少しずつばらばらにスライドイン」を日割り結果で再現する。

- PCのグリッド表示を前提とし、**右端列を最初に**、その後中央列→左列の順で進める。
- 列ごとの差は約90～110ms。各列内のカードは固定の[0, 65, 30, 90]msの並び替えを繰り返す（ランダムではない）。
- 各カードはX=14px→0、Y=0、opacity=.6→1、200～260ms、easeOutCubic系。表示順序そのものは変えず、見た目だけずらす。
- 全体の最後の到着は最大520ms。カードが多い場合は初回の冒頭9～12枚までを演出し、残りは即時表示。
- **モバイル1列表示では右列優先の意味がない**ため、上から下へ30～45ms間隔の軽い順次表示に切り替える。
- スクリーンリーダーとキーボードの読み順は、日付の古い順からのまま。意味のある時間順を動きで逆転させない。
- 長い予定や急な再計算では演出を再発させない。

### MO-08/09: 詳細設定と進捗

- 詳細設定はHTML標準のdetails/summary利用も検討。開閉状態は読めるテキストとaria属性で表現。
- 開閉は160～220msの縦方向。内容が非表示のときはTab移動できないようにする。
- 進捗バーは色幅だけでなく「2/5件 完了」の文字やARIAを含む。実際の完了数と常に一致。

### MO-10: 祝いのピクセル演出（P2）

- 使うとしても「初めて計画を作ったとき」など限定イベントで最大450ms。
- 連続操作時の再発、点滅、画面全体を覆うエフェクトは避ける。
- アニメーションによるアプリの作業効率低下が観測されたら削除する。

## 5. Reduced Motion・安全性・入力方法

- @media (prefers-reduced-motion: reduce) では、装飾的な移動・拡大・staggerを削除または実質0msにし、内容は即座に表示。
- 重要なのは効果の消滅ではなく**情報の同等性**。追加・完了・警告・不足はラベルやメッセージで伝える。
- 各演出中にクリック不可時間を作らない。タスク実行に1秒近い待ちが発生しない。
- タイマーの数字は毎秒更新するが**毎秒アニメーションはしない**。幅固定の数字を使う。
- Focus visible、aria-liveの過剰アナウンス回避、ズーム200%、モバイル縦画面を重点確認。
- 常時明滅・強いグリッチ・大きいスクロール同期は避ける。
- 操作の途中で見た目だけ先に「完了」し、実際の保存に失敗することがないよう状態の一貫性を保つ。

## 6. 実装順序と試験項目

1. **P0** PixelButtonを単体で検証（マウス、タッチ、Enter/Space、連打、disabled、Reduced Motion）。
2. **P0** S0～S3ルートスライド。戻る、履歴、再描画、スクロール位置、フォーカス移動を検証。
3. **P0** タスク追加スナップインと完了ポップ。保存中・保存失敗時の整合を検証。
4. **P1** 時系列カードの順次表示とFLIP並べ替え。多数アイテム・高速操作に耐えるか確認。
5. **P1** グリッドウェーブをPCで確認。スマホ1列では別演出へ切替。
6. **P2** 計画完成時のピクセル装飾を評価。操作負担を増やすなら採用しない。

### 動作確認表

| テスト | 合格条件 |
| --- | --- |
| ボタン押下 | 押すとへこみ、離すと元に戻る。クリックの発火は1回 |
| ドラッグ外れ・キャンセル | pressedが残らない |
| 連続タップ | 二重登録/二重遷移が発生しない |
| 順次表示 | 元のタスク順とスクリーンリーダー順が一致する |
| 画面戻る | アニメ終了に関係なく入力状態を維持 |
| 低速環境 | 60fpsの保証を要求しないが体感的な操作遅延がない |
| Reduced Motion | 全操作可能。メッセージは静止状態で明瞭 |
| iPhone Safari | :active、クリック、ソフトキーボード、画面遷移に異常がない |
| デスクトップ | キーボードフォーカス、文字拡大、タブ操作が可能 |
| タイマー | 毎秒の数字更新で跳ねる/点滅するなどの不要な演出がない |

## 7. 依存ライブラリ・ライセンス

- 初期はCSS Transition/Animationと少量のVanilla JSで実装する。
- WAAPI、FLIPに必要な処理はブラウザ互換性と複雑さを考慮して段階的に追加。
- GSAP等の依存導入は、その機能を必要とする明確な理由があるときのみ比較検討する。
- 参考サイトからコード・素材を複製する際は利用条件を確認する。今回は演出の発想と名称の参照に留め、実装は独自に組み立てる。
